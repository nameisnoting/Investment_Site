## ADR-001: 포트폴리오 구조를 코어/위성으로 분리

**Date**: 초기 설계
**Status**: ✅ 채택

### Context
초기 v1.0은 자산 전체를 개별 종목에만 분배하는 단순 구조였음. 사용자 피드백:
> "개별주뿐만 아니라 안전자산도 필요한 거 아닌가? 포트폴리오의 원칙인가?"

### Options
- A. 개별 종목만 추천 (v1.0 유지)
- B. ETF만 추천 (안전 우선)
- C. **코어(ETF) + 위성(개별주) 이중 구조**

### Decision: C 채택

### Rationale
- **학계 컨센서스**: Bogle/Sharpe 이래 코어-위성 구조가 모던 포트폴리오 이론의 표준
- **실증**: S&P SPIVA 보고서 — 15년 누적 기준 액티브 펀드의 90%가 인덱스에 패배
- **자산 보존 + 알파 추구의 균형**: 코어로 시장 평균 확보, 위성으로 상대 우위 추구
- **버핏 본인 유언**: 사후 아내 유산은 "S&P 500 인덱스 90% + 단기채 10%"

### Consequences
- ✅ 안정성 ↑ (시장 폭락 시 코어가 위성 손실 흡수)
- ✅ 사용자가 "왜 분산?"을 직관적으로 이해
- ❌ 추천 복잡도 ↑ (자산 클래스 2종 관리)

## ADR-002: 위험 성향 슬라이더를 5단계로 결정

**Date**: v4.0
**Status**: ✅ 채택

### Context
사용자 피드백:
> "예금까지 다 동원되는 게 부담스러움. 일부는 그대로 두고 싶음."

위험 성향을 어떻게 입력받을지 결정 필요.

### Options
- A. **자유 입력** (0~100 슬라이더, 무단계)
- B. 4단계 (보수/중간보수/중간공격/공격)
- C. **5단계** (안정적/적당히 안정적/중간/적당히 공격적/공격적)
- D. 7단계 (더 세밀)

### Decision: C 채택

### Rationale
- **4단계의 약점**: "중간"이 없어 사용자가 어느 쪽에 치우치도록 강제됨 (심리적 거부감)
- **7단계의 약점**: 차이가 미세해 사용자가 의미를 인식 못 함 (선택 피로도 ↑)
- **5단계의 강점**: 명확한 중간 + 양 극단 + 양 중간점 = 인지적 부담 최소 + 의미 충분
- **양 극단 라벨만 표시** (안정적 ↔ 공격적): UI 깔끔 + 직관

### Consequences
- ✅ 의사결정 부담 ↓
- ✅ 슬라이더 한 번 움직임 = 큰 변화 (예금 유지율 30%p 점프)
- ❌ 5단계 사이 미세 조정 불가 (필요 시 v2에서 무단계 옵션 추가 가능)

## ADR-003: 자산 tier별 코어/위성 비중 차등 적용

**Date**: v3.0~v4.0
**Status**: ✅ 채택

### Context
자산 1천만원 사용자와 5억원 사용자의 추천이 같아선 안 됨. 자산 적을수록 개별주 분산이 어려움.

### Options
- A. 모든 사용자 동일 비중
- B. **자산 tier 4단계** (starter <3천만 / small <1억 / mid <5억 / large 5억+)
- C. 자산을 연속 함수로 매핑

### Decision: B 채택

### Rationale
- **분산 비용**: 자산 적으면 개별주 1개당 비중이 너무 작아져 의미 없거나 너무 크면 단일 종목 리스크
- **tier별 차등**:
  - starter(<3천만): 코어 80% — 분산 어려우니 ETF 위주
  - small(<1억): 코어 65%
  - mid(<5억): 코어 50%
  - large(5억+): 코어 35% — 분산 가능, 알파 추구 비중 ↑
- **연속 함수의 약점**: 사용자에게 설명 어려움 ("내가 왜 64.7%인가?")

### Consequences
- ✅ 자산 규모 변경 시 추천 변화가 의미 있음
- ✅ 각 tier별 휴리스틱이 명확 → UI에 "starter/small/mid/large" 배지로 표시 가능
- ❌ tier 경계(예: 9,999만원 vs 1억) 사용자는 추천이 갑자기 바뀜 (수용 가능 수준)

## ADR-004: 코어 ETF는 항상 DCA(월 분할매수)로 고정

**Date**: v3.0
**Status**: ✅ 채택

### Context
초기엔 ETF도 개별주처럼 RSI 기반 진입 플랜이 부여됨. 결과 화면에서 ETF에 "🔴 진입 보류 (RSI 78)" 같은 액션이 나오는 게 어색.

### Options
- A. ETF도 RSI 기반 (v1.0 유지)
- B. ETF는 항상 IMMEDIATE
- C. **ETF는 항상 DCA (월 N개월 적립)**

### Decision: C 채택. 적립 기간 N은 자산 tier별 차등 (18/24/36/48개월)

### Rationale
- **ETF는 시장 추종 자산** — 단일 시점 진입 타이밍 의미 ↓, 평균 매입 단가가 더 중요
- **개별주와 본질이 다름**: ETF의 RSI 과열은 시장 자체가 과열이라는 의미 → 회피해도 비슷한 자산 못 사는 함정
- **자산 tier별 차등**:
  - starter 18개월 (자산 적으니 빠르게 채워야)
  - large 48개월 (큰 자산을 일시 투입하면 변동성 노출 ↑)

### Consequences
- ✅ "월 ≈ $200 적립 × 24개월" 같이 실행 가능한 액션 제시
- ✅ 사용자 부담 균형 (목표 비중과 일상 적립의 trade-off 해소)
- ❌ 사용자가 "지금 한 번에 들어가고 싶다" 면 따로 판단 필요

## ADR-005: 시장 분석을 VIX 단일 → 5신호 가중합으로 확장

**Date**: v5.0
**Status**: ✅ 채택

### Context
초기엔 VIX 임계값으로만 매수/관망 판정. 사용자가 정확히 짚음:
> "VIX 지수가 낮을 땐 오히려 팔고 높을 땐 사야 하는 거 아냐? 공포에 사고 탐욕에 팔라고 하잖아"

VIX 단일 cutoff는 트렌드 추종 일변도 + 역발상 시그널 무시.

### Options
- A. VIX 단일 유지 (v1.0)
- B. VIX + 추세 2개 신호
- C. **5개 신호 가중합** (추세/VIX/breadth/금리차/섹터로테이션)
- D. 머신러닝 모델

### Decision: C 채택

### Rationale
- **단일 신호의 약점**: VIX 30↑를 "위험"으로만 보면 시장 저점 매수 기회 놓침
- **5신호 선정 기준**:
  - 학계/업계에서 시장 국면 판단에 자주 쓰이는 지표 중
  - yfinance로 무료 + 즉시 받을 수 있는 것만
- **머신러닝(D) 제외**: 1) 학습 데이터 부족, 2) 블랙박스화 (이 프로젝트의 "투명성" 가치에 반함)

### Consequences
- ✅ composite_score 0~1로 정규화 → equity_ratio 결정의 기반
- ✅ 사용자가 5개 신호 미터바를 직접 보고 의사결정 가능
- ❌ 응답시간 ↑ (섹터 ETF/금리 추가 fetch — 캐시로 완화)

## ADR-006: VIX 역발상 매핑 + 역발상 매수 트리거 (AGGRESSIVE_BUY)

**Date**: v5.0
**Status**: ✅ 채택

### Context
ADR-005의 후속 — 5신호 종합 점수 외에 "공포에 사라"를 별도 트리거로 구현해야 함.

### Options
- A. 공포 신호 없음 (composite_score에만 반영)
- B. **별도 `fear_score` 산출 + 종목 진입 플랜에 직접 영향**

### Decision: B 채택

### Rationale
- **fear_score = VIX 30↑ AND 시장 -15%↓ 동시 충족** 시만 발동
  - 한 조건만으론 함정 (시장 -15% 빠진 후 추세 망가짐만 보일 수도)
- **종목 진입 플랜에 직접 격상**: AGGRESSIVE_BUY 액션 (5분할, 첫 매수 50%)
- **VIX 자체 매핑도 역발상**: VIX 15↓ → 0.20 (안심 = 거품 의심), VIX 32 → 0.85 (공포 = 매수 기회)

### Consequences
- ✅ "공포에 사라"가 코드로 떨어짐
- ✅ 평상시엔 발동 안 함 (오발 ↓)
- ❌ 검증 부족 (실제 시장 폭락 시점에 테스트 안 됨, v2에서 백테스트로 검증 예정)

## ADR-007: 사용자 데이터 저장은 localStorage (서버 DB 없음)

**Date**: v2.0
**Status**: ✅ 채택

### Context
사용자가 같은 입력을 여러 번 하는 게 귀찮음 → 저장 필요.

### Options
- A. **브라우저 localStorage** (최대 5개 자동 회전)
- B. 서버 DB (SQLite/PostgreSQL)
- C. 둘 다 (옵션 제공)

### Decision: A 채택

### Rationale
- **A의 장점**:
  - 자산 정보가 서버로 안 감 → **프라이버시 ↑** (이 도구의 핵심 신뢰 요소)
  - 서버 인프라 비용 0
  - 사용자 인증 불필요 → 진입 마찰 ↓
- **B의 약점**:
  - 자산 정보 저장은 법적 의무 ↑ (개인정보 보호)
  - 무료 호스팅에선 DB 인프라 추가 비용/복잡도
- **수용한 trade-off**: 다른 기기/시크릿 모드에선 안 보임 (의도된 동작)

### Consequences
- ✅ 인프라 단순, 운영 비용 0
- ✅ 사용자 신뢰 ↑ ("내 자산이 어디 저장되는지 명확")
- ❌ 동기화 불가 (v2에서 옵트인 클라우드 동기화 가능)

## ADR-008: Vanilla HTML/JS 선택 (React/Next.js 거부)

**Date**: 초기 설계
**Status**: ✅ 채택

### Context
프론트엔드 프레임워크 선택.

### Options
- A. **Vanilla HTML/CSS/JS**
- B. React + Vite
- C. Next.js
- D. Vue.js

### Decision: A 채택

### Rationale
- **앱 규모**: 페이지 1개, 상태 단순 (폼 입력 + 결과 표시)
- **React/Next.js는 오버킬**:
  - 빌드 단계 추가 (Webpack/Vite)
  - npm 패키지 수백 개
  - 학습/유지보수 비용 ↑
- **Vanilla의 장점**:
  - 빌드 단계 0 (저장 → 새로고침 → 끝)
  - 의존성 0 (브라우저 기능만)
  - 배포 단순 (Flask가 static 폴더만 서빙)

### Consequences
- ✅ 개발 속도 빠름
- ✅ 배포 파이프라인 단순
- ❌ 페이지 늘어나면 라우팅 등 직접 구현 필요 (v2에서 라우터 추가 시 재고)

## ADR-009: 배포 플랫폼으로 Render 선택 (Vercel 거부)

**Date**: 배포 단계
**Status**: ✅ 채택

### Context
실제 웹사이트로 배포 필요. 포트폴리오용이라 안정성 우선.

### Options
- A. **Render** (무료 플랜)
- B. Vercel
- C. Railway / Fly.io
- D. AWS EC2 / Oracle Cloud Free VM

### Decision: A 채택

### Rationale
- **Vercel 제외 이유**:
  - Serverless라 함수 timeout 10초 (무료) — 우리 첫 분석 ~45초
  - 디스크 캐시 매 요청마다 초기화 → yfinance/Finnhub 캐시 무의미
  - throttle 상태 변수 유지 불가
- **Render의 강점**:
  - 컨테이너 상시 가동 → Flask가 계속 살아있음
  - GitHub 연동 자동 재배포
  - 무료 플랜으로 시작 가능
- **D 제외**: 직접 서버 운영(Nginx/SSL/방화벽) 부담

### Consequences
- ✅ 첫 분석 timeout 안전, 캐시 정상 작동
- ❌ 무료 플랜은 15분 미사용 시 sleep (다시 깨우는 데 30초)
- 💰 본격 운영 시 $7/월로 sleep 제거 가능

## ADR-010: 펀더멘털 데이터 소스 2단계 피벗 (yfinance → Twelve Data → Finnhub)

**Date**: v6.0 (배포 후 운영 단계)
**Status**: ✅ 채택

### Context
Render 배포 직후 발견:
- yfinance의 `info()` API가 Render 공유 IP에서 **Yahoo로부터 rate limit 차단**
- 결과: 코어 ETF만 나오고 개별주 0개 — 핵심 가치 손상

### Options
- A. yfinance 유지 + User-Agent 등 우회 시도 (효과 ↓)
- B. Render 유료 플랜 ($7/월 → 다른 IP)
- C. **다른 데이터 API로 교체**
- D. Oracle Cloud Free VM으로 이전 (전용 IP)

### Decision: C 채택 (2단계 피벗)

**1차 시도 — Twelve Data**: 실패
- 가입/통합 완료 후 발견 — 무료 플랜은 사실상 AAPL 1종목만 statistics 응답
- 다른 종목들은 "exclusively with pro plans" 차단

**2차 시도 — Finnhub**: 성공
- 키 기반 인증이라 IP 차단 우회
- 미국 주식 전체 펀더멘털 무료 (60회/분)
- 미국 14개 종목 모두 정상 응답 확인

### Rationale
- **2단계 피벗이 필요했던 이유**: API 무료 플랜의 실제 제약은 문서에 명시 안 됨 → 직접 테스트로만 검증 가능
- **PM 관점 학습**: "무료 API의 한도는 액면 그대로 믿지 말고 실제 사용 케이스로 검증해야 함"

### Consequences
- ✅ 개별주 추천 정상 동작 (15/20 종목 통과)
- ✅ 첫 분석 시간 ~190초 → ~45초로 단축 (Finnhub throttle이 Twelve Data의 1/7)
- ❌ 한국 종목 풀 비활성 (Finnhub 무료 한국 미지원) → ADR-011 참조

## ADR-011: 한국 종목 풀 비활성 + EWY ETF로 대체

**Date**: v6.0
**Status**: ⚠️ 임시 채택 (v2에서 재검토)

### Context
ADR-010 이후 한국 종목 어떻게 처리할지 결정 필요.

### Options
- A. yfinance로 시도 (Render에서 차단 가능성 높음)
- B. **한국 풀 제거 + EWY (iShares MSCI Korea ETF) 코어에 추가**
- C. Twelve Data Grow 유료 ($29/월)
- D. DART Open API (한국 금융감독원) 통합 — 작업 큼

### Decision: B 채택 (v1 한정)

### Rationale
- **단기 안정성 우선**: 배포 직후 작동하는 것이 v1 핵심 가치
- **EWY로 한국 노출 유지**: 한국 시장 자체 추적은 ETF로 가능
- **v2에서 D 검토 예정**: 본래 의도(한국 개별주 추천)는 이 도구의 차별점

### Consequences
- ✅ 안정성 확보, 한국 노출 완전 차단은 아님
- ❌ 개별 한국 종목 추천 불가 — **이 프로젝트의 원래 비전 미완**
- 📋 v2 로드맵 우선순위 1번으로 명시

### Aspirational Note

## ADR-012: 포트폴리오 전략을 4모드로 분리 (장기/폭등/모멘텀/혼합)

**Date**: v7.0
**Status**: ✅ 채택

### Context
사용자 피드백:
> "너무 뻔한 주식만 추천함. 장기투자에는 적합하지만, 단기에 부자가 되고 싶은 욕망을 이용할 수 없음."

기존 v1~v6은 우량주 펀더멘털 기반 장기투자 일변도. 사용자의 다양한 투자 니즈(단기 알파, 폭등 포착)를 못 채움.

### Options
- A. 슬라이더 한 축으로 모든 걸 표현 (안정↔공격이 곧 장기↔단기?)
- B. **전략 모드 드롭다운 4종으로 분리**
- C. 슬라이더 2개 (위험 + 시간지평)

### Decision: B 채택

### Rationale
- **차원 분리의 이점**: '위험 성향'(안정/공격)과 '전략'(장기/단기)은 다른 차원. 한 슬라이더에 묶으면 사용자가 본인 의도를 표현 못함
- **드롭다운이 직관**: 4개 옵션을 description과 함께 보여주면 사용자가 본인 상황에 맞게 선택 가능
- **C의 약점**: 두 슬라이더가 곱셈으로 작용하면 결과 예측 어려움 + UI 복잡

### Consequences
- ✅ 같은 사용자 입력으로 4가지 다른 결과 비교 가능
- ✅ 위험 슬라이더는 모드 내 세부 조정에 집중 (예: 폭등 모드에서 레버리지 비중)
- ❌ 평가 코드 복잡도 ↑ (Screener에 3개 추가 스코어링 메서드)

## ADR-013: 폭등시그널 풀 + 레버리지 ETF 채택 (BND/SCHD 제거)

**Date**: v8.0
**Status**: ✅ 채택

### Context
폭등시그널 모드의 코어 ETF를 어떻게 구성할 것인가? 위성 종목은?

### Decision
- **코어 ETF**: VOO(55%) + QQQ(45%)만. BND(채권)/SCHD(배당)는 제거 — 폭등 모드와 안 맞음.
- **레버리지 ETF**: TQQQ(40%) + SOXL(30%) + UPRO(30%). risk_level별 0~30%
- **위성 풀 24종목**: SaaS(NET/DDOG/SNOW...) + 핀테크(SOFI/AFRM/COIN...) + AI(PLTR/AI/IONQ...) + 신흥그로스(DUOL/APP/CELH/MNDY)

### Rationale
- **레버리지 ETF는 폭등 모드의 핵심**: 일일 변동성 3배 노출이 폭등 추구의 직접 도구
- **시장 약세(composite<0.5) 시 레버리지 자동 50% 축소**: 폭등 추구도 시장 국면은 따라야 함 (자체 안전장치)
- **위성 24종목 선정 기준**: Finnhub 무료에서 펀더멘털 데이터 받아지는 종목 + 매출 성장 + 변동성 있는 그로스주
- **PEG 무력화**: Finnhub 무료는 PEG 미제공 → PEG 항목 제거, 매출 성장으로 대체

### Consequences
- ✅ "월 100만 자산으로도 폭등 노출 가능" (TQQQ 한 주만 사도 큰 변동성)
- ❌ 변동성 손실(decay) 리스크 명시 필요 → UI에 경고 박스 추가

## ADR-014: 모멘텀 추종 모드는 동적 풀 + 가격 데이터만

**Date**: v8.1
**Status**: ✅ 채택

### Context
모멘텀 추종은 "지금 강하게 오르는 종목 올라타기". 고정 풀로는 추세가 끝난 종목을 계속 보는 함정.

### Options
- A. 고정 풀 (us_pool + surge_pool)
- B. **동적 필터링**: 베이스 풀 합집합에서 매번 30일 모멘텀 +15%↑ 종목만 통과
- C. 외부 모멘텀 랭킹 API 통합 (유료)

### Decision: B 채택

### Rationale
- **고정 풀의 함정**: 작년 강했던 NVDA를 올해도 추천 → 추세 끝났을 때 손실
- **30일 +15% 컷오프**: 충분히 강한 추세만 필터링. 약세장에선 통과 종목 0개 → 사용자에게 "현금 유지 권장" 안내
- **펀더멘털 무시**: 모멘텀 모드는 가격이 핵심. info() 호출 안 함 → 응답 속도 5~10배 빠름 (2.8초)

### Consequences
- ✅ 시장 환경 자동 반영 (강세장 = 후보 많음, 약세장 = 거의 없음)
- ✅ 펀더멘털 API 호출 없어서 빠름
- ❌ 가격만으로는 잘못된 추세 (펌프 앤 덤프) 못 거름 → RSI 90+ + 모멘텀 둔화 시 AVOID 추가로 보완

## ADR-015: 혼합 모드는 risk_level별 가중 합성 매트릭스

**Date**: v8.2
**Status**: ✅ 채택

### Context
혼합 모드는 3개 모드(장기/폭등/모멘텀)를 어떻게 섞을지 결정 필요.

### Decision
risk_level별 [장기, 폭등, 모멘텀] 가중치 매트릭스:

| risk_level | 장기 | 폭등 | 모멘텀 |
|-----------|------|------|--------|
| 1 (안정)  | 80% | 15% | 5% |
| 2         | 65% | 25% | 10% |
| 3 (중간)  | **50%** | **30%** | **20%** |
| 4         | 35% | 35% | 30% |
| 5 (공격)  | 20% | 40% | 40% |

같은 ticker가 여러 모드에 나오면 비중 합산. cash_pct는 가중 평균.

### Rationale
- **안정 측도 폭등/모멘텀 일부 노출**: 100% 장기는 너무 보수적. 5%라도 단기 노출이 있어야 학습 효과
- **공격 측도 장기 20% 유지**: 100% 폭등/모멘텀은 위험. 안전 닻으로 장기 20%
- **3과 4 사이 점프**: 중간(3)은 보수 쪽으로 약간 기울임 (50/30/20). 공격(4)부터 공격 쪽으로 확실히 이동
- **중복 종목 비중 합산**: NVDA가 장기에도 폭등에도 추천될 수 있음 — 의미 있음 (강한 신호)

### Consequences
- ✅ 한 화면에 다양한 전략의 종목 추천 (11종목 등)
- ✅ 결과가 "어디서 왔는지" 추적 가능 (mixed_weights 필드)
- ❌ 같은 ticker가 모드별로 다른 의도(장기 보유 vs 단기 추격)인데 비중 합산 시 의도 잃음

## ADR-016: 백테스팅을 buy-and-hold + 요청 시 실행으로 결정

**Date**: v9.0
**Status**: ✅ 채택

### Context
백테스팅 어떻게 구현할까? 정확도와 속도/구현 비용 트레이드오프.

### Options
- A. **Buy-and-hold + 요청 시만 실행**
- B. 정기 리밸런싱 (월/분기)
- C. 워크포워드 (매 시점 추천 다시 받기)

### Decision: A 채택 (v1), B/C는 v2 로드맵

### Rationale
- **추천 정확도 검증이 1차 목표**: 현재 시점 추천이 과거에 통했을지 보는 게 핵심
- **A의 한계 명시화**: survivorship bias (지금 추천된 종목은 지금까지 살아남은 것) + 리밸런싱 미반영
- **요청 시만 실행**: 모든 추천에 백테스팅 붙이면 응답 느려짐. 사용자가 명시적으로 보고 싶을 때만
- **3개 기간 (1/3/5년)**: 1년 = 최근 성과, 3년 = 사이클, 5년 = 장기 — 다른 정보 가치

### Consequences
- ✅ 평소 추천은 빠르게 (1.5초), 백테스팅은 별도 (~3초)
- ✅ SVG 차트 직접 구현 — Chart.js 의존성 없음
- ❌ Survivorship bias 있음 (사용자에게 명시화)

## ADR-017: NaN/Inf → null 자동 sanitize (운영 안정성)

**Date**: v9.1 (버그 픽스)
**Status**: ✅ 채택

### Context
배포 직후 발견: "JSON.parse Unexpected token N, ...price_vs_ma200_pct:NaN..."
- 한국 시장 데이터 부족 시 ma200 계산이 NaN
- Python의 json.dumps는 기본적으로 NaN을 그대로 직렬화 ({"x": NaN})
- 표준 JSON엔 NaN이 없어서 JavaScript의 JSON.parse가 거부

### Options
- A. 각 NaN 발생 지점에서 if isnan check
- B. **전역 sanitize 함수로 응답 직전 일괄 처리**
- C. Flask custom JSON encoder

### Decision: B 채택

### Rationale
- **A의 약점**: 새 코드 추가할 때마다 NaN 체크 까먹기 쉬움 → 동일 버그 재발
- **B의 강점**: dict/list 재귀 순회로 한 곳에서 모든 응답 처리. 미래의 버그도 예방
- **numbers.Real 확장**: yfinance는 numpy.float64 반환 → isinstance(x, float) 통과 X. 발견 후 numbers.Real로 확장
- **문자열 "+nan%"도 정리**: detail 같은 표시용 텍스트에서 "MA200 +nan%" 같은 잔재 방지

### Consequences
- ✅ 클라이언트가 모든 응답을 안정적으로 parse
- ✅ 향후 새 필드 추가해도 자동으로 보호됨
- ❌ 응답에 NaN이 있던 필드는 null로 바뀜 → 클라이언트는 null 체크 추가 필요 (이미 적용)

### 학습
- **무료 호스팅에선 데이터 깨짐이 흔함** — 견고한 sanitize는 필수
- **numpy 타입은 Python 타입과 다르게 동작** — isinstance 체크 시 주의
